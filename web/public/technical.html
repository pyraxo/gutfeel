Behind the browser version

How the old game runs in a browser.

Gut Feel expects an old Windows computer and a multiplayer server from the same era. To get it working in a browser, I had to give the original game code a way to run and rebuild the services it depended on.

The game still uses its original rules, artwork, and sound. The Host runs the team session, and players exchange messages in the original format.

The browser version adds the software to run those files, connect players through a lobby server, and display their reports.

01

Original system

The game is still a Director program

Gut Feel was made in Adobe Director, which packages interactive programs as "movies". Despite the name, these are executable game files: they respond to your input and contain the instructions for what happens next.

The game has three main movies. Each player runs the Client, while the Tutorial provides a separate practice mode. The Host manages the team roster, starts the scenario, and keeps the scores and reports.

Inside those files, code written in Director's Lingo language controls the rooms, scoring rules, and messages between players. The browser version runs that recovered code with the game's original artwork and sound.

02

Browser runtime

DirPlayer runs the movies

Browsers cannot run Director movies on their own. This version uses DirPlayer, a runtime that reads the movies and executes their instructions. It handles the pictures and sound as well as input from the player.

DirPlayer is written in Rust and compiled to WebAssembly, a program format that browsers can execute. Once it loads, it provides the environment the game needs to run. I added compatibility changes for behavior Gut Feel relies on.

Director also used plugins called Xtras for things such as network connections and Windows services. The browser runtime implements the functions this game needs, though some desktop functions remain unsupported.

04

Compatibility

Replacing the old service calls

The game still asks for services at its old addresses. A small piece of browser code, called the bridge, redirects the supported requests to this website. It also chooses the connection for each network request and attaches the player's lobby information.

Other bits of compatibility code, called adapters, handle individual jobs such as reading configuration, accepting input, and exporting a report. Each one lets the original game request a familiar operation while the browser does the work.

Loading configuration

The game expects to read a configuration value immediately, but a browser may have to wait for a file to download. I load the file before starting the movie, so the adapter already has the values when the game asks for them.

The Client and Tutorial use different configuration files. Keeping their paths separate prevents one mode from receiving the other's settings.

05

Startup

How a multiplayer game starts

  1. The browser loads the page and the DirPlayer runtime.
  2. The lobby service creates the session or admits the invited player.
  3. The browser downloads the selected movie's configuration before DirPlayer starts the movie.
  4. On the creator's page, the original Host starts in its own frame with the facilitator credential.
  5. Each Client connects to the lobby relay and joins the team. The lobby marks that player as ready.
  6. The creator selects a scenario and starts the session.
  7. The original Host finishes its setup and sends the start message. Play then continues through the browser runtime.

Training starts its own movie with its own configuration, so you can play it without creating a multiplayer lobby.

06

Network

Getting players into the same game

The lobby service

A lobby groups up to five players into one temporary session, including the person who creates it. Through the lobby service's API, the browser can create or join a session, get its status, leave, or end the game.

The server keeps the player list and checks who can do what. Each player receives a private credential that identifies their role. The creator gets a second credential to act as the facilitator. Neither credential appears in the invite link.

Why the Host still exists

The creator's page runs the original Host in a separate frame, using the facilitator credential. That lets the creator play normally while the Host handles team setup, records scores, and prepares reports. The Host does not occupy a player slot.

Starting a game involves both systems. The lobby service checks that the Host and every registered player are ready, then changes the status to starting. The Host completes its original setup and sends the start message. Only then does the server mark the session as running.

The relay

The game still sends messages in the Director Multiuser protocol, the format understood by the original movies. The runtime sends them over WebSockets, connections that stay open so the browser can exchange messages throughout a session.

Each lobby has its own relay on the server to forward those messages. It keeps players, groups, and peer connections separate from those in other lobbies.

In the desktop game, each player also has a peer host that accepts connections from other players. A browser cannot accept that kind of connection, so the server provides a route for each peer host instead. These routes preserve who sends messages to whom. All traffic goes through the server; there are no direct WebRTC connections between browsers.

07

Reports

The Host still writes the results

The original Host produces an AMR report containing XML, a text format with named fields for the players, scores, scenario, and room results.

To make the download work, a file adapter saves the Host's output in the runtime's memory. An archive adapter can then package that AMR file into a ZIP. Both preserve the report's contents, including the scores the Host calculated.

The report page reads an AMR file or a supported ZIP, displays the recorded results, and prepares them for printing.

Open a report

  1. Open the report page.
  2. Select an AMR file or a ZIP file that contains an AMR report.
  3. Select the scenario and team that you want to inspect.
  4. Use the browser print command to print the report or save a PDF.

Because the report omits some game events, the viewer cannot independently recalculate the complete final score. It displays the values recorded by the Host.

08

Access

The server separates teams and roles

Every connection must belong to a lobby and have a valid credential for its role. A player's credential cannot operate the facilitator controls, and later connections must use the same game identity as the first one.

For public hosting, the server also checks the website's origin: its scheme, hostname, and port. Requests from a different origin are rejected. HTTPS encrypts web traffic, and WSS does the same for WebSocket messages.

If you host a server

WebSocket connection addresses include a credential. Configure your proxy and access logs to omit that value so it does not end up in a log file.

This protects lobby access, but the original game still trusts its invited players to send valid gameplay actions. It is not a complete anti-cheat system.

09

Repository

The public source includes the playable game

The public repository includes the browser-ready movies, artwork, sound, manuals, compatibility code, and server required to run a complete copy.

The original materials retain their own copyright and are separate from the GPL licence for the browser compatibility code.

The source tests cover the replacement code, including its network and input behavior.

The repository records the size and SHA-256 hash of each preserved input file. Comparing these values tells you whether a file matches the preserved copy. It cannot tell you whether every part of the game behaves correctly in the browser.

10

Limits

What still needs work

  • Some behavior still needs comparison with the original game, including a full five-player digestion session from start to finish.
  • Testing on physical phones is still outstanding.
  • Lobby data exists only in server memory, so restarting the server ends active games.
  • The facilitator can reconnect while players are waiting. During startup or play, losing that connection ends the lobby because the game cannot replace its Host or restore the match.
  • The service currently runs as one application instance.
  • Some functions from the old desktop components are still unsupported.
